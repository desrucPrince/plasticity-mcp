# Changelog

## Unreleased

- Tools from a real multi-part build (2026-11-18; `accept:native-tools-2026-11`). (1) `overwrite: true` on every tool that writes a file at a caller-given path: `plasticity_export_step`, `_parasolid`, `_iges`, `_sat`, `_stl`, `_3mf`, `_obj`, `_svg`, `_hiddenline_svg`, `plasticity_screenshot` (with `path`) and `plasticity_save_copy`. Default unchanged: an existing path is refused before the export, and the refusal now names the option. The refusal was the server's own (`assertAbsent` before the export and an exclusive copy after it), not Plasticity's. With `overwrite: true` a regular file is replaced (a directory, a symbolic link and any other entry are refused; the path is checked before the export and again before the rename): the validated file is written to a temporary file in the output's folder and renamed over the target, so a failed export leaves the old file byte-identical and no temporary file. `plasticity_open_document` never overwrites its backup. (2) Long undo and redo: `plasticity_undo` / `plasticity_redo` take up to 5,000 `steps` (was 500) and return `stepsRequested`, `stepsDone`, `stepsRemaining`. Cause of the "CDP request timed out: Runtime.callFunctionOn" on several hundred steps: every step was one request whose page-side wait looked at Plasticity's undo promise only when a 25 ms timer fired and whose own deadline (10 s) equalled the request limit, and a full document read followed every step (measured 41 ms a step where the undo itself takes 0.6 ms; a slow step could only end as a request time-out, which left the session uncertain). Now a step ends when the promise settles, each step is still its own request, and the document is read once at the end. A request that times out part-way is not retried and the run stops: the tool waits for that step to end (the page keeps a record of it), reconciles, and returns a definite count (`stopped: "timed-out"`, a normal reply); when the step's fate or the depths cannot be proven the session stays uncertain as before. `plasticity_batch` `undoOnError` and the recipes' own undo behave as before. (3) `plasticity_check_interference` (still read-only; the three status values are unchanged, fields are added): `interfere` carries `overlapVolumeMm3` (the kernel's mass properties of the intersection bodies, read in the temporary database before they are removed; 400.0000000000001 mm3 for two boxes sharing 4 x 10 x 10 mm; it agreed with analytic values to about 1e-15 relative on overlaps bounded by planar faces and to within 1e-4 relative on overlaps bounded by curved faces (largest measured error 6.2e-5), and it is not a proof of an exact value on curved overlaps), `overlapBoundsMm` and a `volumeMm3` per intersection body; `no-volumetric-interference` carries `overlapVolumeMm3: 0`. Coplanar contact: where the intersection fails in the kernel in one body order (`PK_BODY_boolean_2` error `21653` in the field; not reproduced on test bodies), the reversed order and the kernel's clash test decide: "no effect" plus abutments only is `no-volumetric-interference` with the new reason `contact-without-volume` (was `unsupported` / `native-intersection-failed`). Correction found on the way: "Operation has no effect" is also the kernel's answer for a target that lies strictly inside the tool, so a body inside another read `no-volumetric-interference` when it came first in the pair; it is `interfere` with its whole volume now (the reversed order makes the body), and a "no effect" that the clash test or the reversed order does not confirm as empty is `unsupported` (`native-intersection-not-proven-empty`). `kernelEvidence` shows the kernel's answers. (4) No `plasticity_measure_body_clearance`: Plasticity 26.1.3 exposes no minimum distance between two solids; the one exact range read that is reachable (`ProfileCollection.DiagnoseIntersections`) measures a body against a wire body only (`discovery/tools-2026-11/FINDINGS.md`), and an estimate is not shipped.
- Selection guard, review round 4. (1) A default gizmo the user is editing is no longer cancelled. A default command counts as idle only while it is untouched (its factory reads `none`, it holds no temporary objects and does not flag its factory as changed); a dragged gizmo reads `updated` with a preview (measured live with a real drag, held and released; a value typed into the dialog was not measured), and the guard, its watcher and `plasticity_reconcile` leave it. An edit is refused then with "Plasticity is busy: the user is editing ... Nothing was changed" (from the state read, which Plasticity refuses while a preview is held, or from the guard), and reconcile names the gizmo: in its error while the preview is held (Plasticity refuses the read reconcile needs, so the session is not reconciled then), in `recovery.activeCommand` with `edited: true` when the document can be read. Only sources that run a command are wrapped in the guard: exports, section analyses, save-copy, setting the workplane and the label refresh of a read no longer touch the selection or any gizmo (12 `mutate()` sites, pinned by name in the site test, which now uses the runtime's own predicate); opening a document keeps the guard by its own word (`selectionGuard: true`). (2) A guarded source that outlives its call no longer degrades the window: the watcher stops at the call's timeout, a source that settles late puts the saved selection back only into an empty selection (a newer selection of the user wins), and `plasticity_reconcile` puts an abandoned guard's selection back when nothing is selected (`recovery.restoredSelection`). (3) `plasticity_transfer_holes`: the thin-wall guard beside a bore and beside the wall of a counterbore no longer depends on the wall's angle (beside a countersink cone it still does: only the ring of rays looks there). After the ray guards the plan measures the cylindrical walls of the cut, the bore and the wall of a counterbore (a countersink cone and the floors keep their own guards and messages; a wall that ends on a floor of the cut is measured down to 0.05 mm above it), against every target face the cut does not pass through, with the kernel's exact point-to-face distance and a bound that needs no sampling: a face nearer than 0.045 mm at any point refuses the cut before the edit, 0.05 mm or more is never refused, in between either can happen. Ø4 beside a Ø6 hole with a wall of 0.002, 0.01 and 0.04 mm is refused at 0, 10, 22.5, 45, 67.5 and 90 degrees (it was cut at 10, 22.5 and 67.5), and so is a Ø3 bore 0.002 to 0.04 mm from a pocket wall turned 22.5 degrees. The reply has `clearance` (reads, calls, ms; measured: nothing read when no face is within about 1 mm, 18 to 33 ms for one bore 0.06 mm from a wall, 41 to 53 ms for 12 bores that all lie 0.06 mm from an edge). (4) The static site test also rejects command sources written as plain or concatenated strings, through an aliased editor, `executor.enqueue`, `['exec']`, `.undo()`/`.redo()` through an alias, a direct `command.execute()`, a constant imported from another file, and an opt-out that is not a literal in the `mutate()` call. (5) `plasticity_boolean` says that a containing-tool intersection with `keepTools` still adds one Undo step; `plasticity_undo`/`plasticity_redo` say that a step whose state holds a selected face or edge takes up to 0.25 s longer.
- Edits no longer hang on the selection. With a face or an edge of a body the edit does not touch selected (by `plasticity_select_faces`, or by a person at the window), any edit used to commit and then never return: 10 s, "CDP request timed out: Runtime.callFunctionOn", `OffsetFaceCommand` left `Awaiting`, session uncertain. Cause: after a command that finished, Plasticity starts the default command of the current selection, which waits for the user, and the `exec()` that ran the edit stays pending. Now every native command the server runs (all 171 `runtime.mutate()` command sources: direct calls, `plasticity_batch` steps, `plasticity_undo`/`plasticity_redo`, the Dimension and Align commands) runs inside one selection guard in `PlasticityRuntime.mutate`: the selection is saved and emptied before the command and put back after it, on success and on failure. Items whose body version is gone are left out (a face or edge of a rebuilt body, everything of a deleted body); a whole body the edit changed stays selected. A default command that idles in `Awaiting` at entry (the gizmo of the selection) is cancelled and not started again; the guard cancels nothing else, and with a command of the user active it stands aside (the edit runs as before, and the selection is put back when Plasticity's interrupt left it empty). A state read does not go through the guard (its label refresh runs no command). `plasticity_undo`/`plasticity_redo` wait for the history step to settle instead of returning when the Undo stack shrinks, and a default command the step chains is cancelled. `plasticity_reconcile` cancels an idle default command that an older call left behind and says so (`recovery.cancelledDefaultCommands`); nothing is undone or repeated. `plasticity_set_driving_distance`, `plasticity_move_measurement_label` and the profile delete of `plasticity_create_rib` / `plasticity_create_countersink(_pattern)` now put the selection back. A problem inside the guard never replaces a call's result: it is written to the server log (`[plasticity-mcp] selection guard: ...`). Overhead with nothing selected: 0.3 to 0.6 ms per native call that runs a command (measured in five runs: 0.27, 0.31, 0.31, 0.33 and 0.59 ms; the review measured 0.5 ms; two runs on the tree of review round 4: 0.45 and 0.54 ms); a call that runs no command is not wrapped. A test fails when a command source is sent with `read()`/`readNative()` instead of `mutate()`. Live: `npm run accept:native-selection` (13 tools x 8 selection states, 20 edits in a row, entry states, recovery, interleaved speed check). Measured behaviour: `discovery/probes-2026-11-pick/FINDINGS.md`, "Selection and default commands".
